# moon-validate

月相计算的验证工具。这里的脚本不参与打包，只用来保证 `data/MoonCalculator.kt` 的数值可信。

## 算法

`app/src/main/java/com/gnsstoolkit/data/MoonCalculator.kt` 用 Meeus《Astronomical Algorithms》：

* 第 47 章月球黄经，截断到前 20 个周期项（系数绝对值 > 7000）；
* 第 25 章太阳黄经（低精度式）；
* 月-日黄经差 0° = 新月，180° = 满月；
* 照明面积比 `k = (1 - cos Δλ) / 2`；
* 下次新月/满月用「6 小时粗扫定位过零点 + 二分 40 次」求解，精度约 1 秒。

不做 ΔT 与章动修正：本应用只显示月相形状和月龄，分钟级偏差不可见。

## 验证

`moon.py` 是同一算法的 Python 原型，三种检验：

```
python3 moon.py
```

1. **Meeus 47.a 算例** —— 月球黄经级数本身。截断到 20 项的结果 `133.162299°`，书上是 `133.162655°`，差 `0.0004°`。
2. **日食/月食时刻对照** —— 端到端检验。7 次日月食里，算出的朔/望时刻与最大食时刻相差 `-7.1 ~ +7.4` 分钟。这个偏差主要是「朔 ≠ 最大食」的几何差，不是算法误差（最大食时刻取决于影轴与地心最近，通常晚于朔数分钟到半小时）。
3. **固定基准点** —— 下面的数字供 Kotlin 侧回归。

```
2026-10-31 12:00  elong=252.281  illum=65.22%  age=20.84d  next_new=2026-11-09 07:03  next_full=2026-11-24 14:58
2026-01-01 00:00  elong=146.149  illum=91.52%  age=11.93d  next_new=2026-01-18 19:54  next_full=2026-01-03 10:04
2024-04-08 18:17  elong=359.947  illum= 0.00%  age=29.39d  next_new=2024-05-08 03:25  next_full=2024-04-23 23:51
2025-03-14 06:58  elong=180.019  illum=100.00% age=14.26d  next_new=2025-03-29 10:58  next_full=2025-04-13 00:23
```

`2024-04-08 18:17` 是北美日全食，`2025-03-14 06:58` 是月全食，两个极端相位正好互为对照。

## Kotlin 侧回归

`run-bench.sh` 把 `MoonCalculator.kt` 的算法部分原样抽成 `Bench.kt`（`regen.py` 负责这一步，去掉 Android 依赖、把 `private` 开成 `internal`），用 Kotlin 编译器编译到纯 JVM 上跑，和上面的基准值逐点比对：

```
JAVA_HOME=/sd/Ubuntu/opt/jdks/jdk21 bash run-bench.sh
```

当前结果：elongation 最大偏差 `0.00057°`（浮点差），照明比例与月龄偏差 `0.00`，下次朔望时刻与 Python 完全一致。

**改了 `MoonCalculator.kt` 必须重跑**，`run-bench.sh` 会自动调 `regen.py` 重新生成 `Bench.kt`。

## 一个容易踩的坑

月龄有两种算法：

* `Δλ / 360 × 29.53`（按平均角速度折算）；
* `当前时刻 - 上一次新月时刻`（真实间隔）。

两者可以差到半天，因为朔望月长度在 29.27–29.83 天之间变化。应用里用的是后者。早期版本用前者，满月时月龄显示 14.77 天，而真实值是 14.26 天。
